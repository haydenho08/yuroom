# Deploying YURoom

YURoom is one Docker image (the Spring Boot API serving the React build) plus one PostgreSQL 16
database. Any host that runs a container and gives you a Postgres will do; the image has no
host-specific code.

## What the image expects

| Variable | Required | Meaning |
|---|---|---|
| `DATABASE_URL` | yes | Either `postgres://user:pass@host:5432/db` (what most hosts give you; translated automatically) or a `jdbc:postgresql://…` URL with `DATABASE_USERNAME` / `DATABASE_PASSWORD` |
| `PORT` | no (8080) | Port to listen on; most platforms set it |
| `DEMO_DATA` | no (`true`) | Shows the "Demo data" banner. Set `false` **only** once the real timetable is loaded with permission |
| `INGESTION_FILE_PATH` | no | Defaults to the synthetic demo timetable baked into the image |
| `DB_POOL_SIZE` | no (5) | Keep at or below your Postgres plan's connection limit |
| `SERVER_TOMCAT_REMOTEIP_INTERNAL_PROXIES` | only if needed | Regex of the host's proxy IPs, if they're not private addresses (see below) |

The image runs with `SPRING_PROFILES_ACTIVE=prod`, as a non-root user, with a `/actuator/health`
health check. The JVM is sized to 60% of the container's memory and fits in a 512 MB instance (about 265 MB measured).

## Heroku, step by step (do this yourself; it needs your accounts)
1. Claim the GitHub Student Developer Pack, then the Heroku offer.
2. Install the Heroku CLI, then: `heroku create yuroom-<something>` and `heroku stack:set container`.
3. Add a `heroku.yml` at the repo root:
   ```yaml
   build:
     docker:
       web: Dockerfile
   ```
4. `heroku addons:create heroku-postgresql:essential-0` (this sets `DATABASE_URL`).
5. `heroku config:set DEMO_DATA=true`
6. Deploy: `git push heroku main`, or connect the GitHub repo in the dashboard with "wait for CI to pass" turned on.
7. Check: `heroku logs --tail` shows `Started YuroomApplication` and `Ingestion run 1 SUCCESS`, and
   `/actuator/health` returns `{"status":"UP"}`.

## The proxy and client IPs (important for rate limits)
Every platform puts a reverse proxy in front of the app. Without configuration, every request would
appear to come from that proxy, so all students would share one rate limit. The `prod` profile turns
on Tomcat's `RemoteIpValve` (`server.forward-headers-strategy: native`):

- It trusts `X-Forwarded-For` **only** when the TCP connection comes from a trusted proxy address
  (private ranges by default: 10/8, 172.16/12, 192.168/16, 100.64/10, 127/8, …).
- It reads the header **from the right**, skipping trusted hops, and takes the first untrusted address.
  The proxy appends the real client address last, so anything the client typed further left is ignored.
  `RealTomcatIntegrationTest` proves a spoofed header doesn't change the rate-limit key.

**After the first deploy, verify it:** report the same room from your phone on Wi-Fi and then on mobile data.
Both should succeed, because they're different addresses. A second report on the same network should get the
"already reported" message. If *everything* is rate-limited together, the proxy's addresses aren't private:
set `SERVER_TOMCAT_REMOTEIP_INTERNAL_PROXIES` to a regex matching exactly the host's documented proxy range.

## Real timetable data (only with permission)
The demo image ships `data/sample/timetable-demo.csv` (synthetic, generated by
`scripts/GenerateDemoTimetable.java`). Real York data must never be committed or baked into an image.
Once the Registrar agrees, the options are an approved URL (`INGESTION_SOURCE=HTTP` + `INGESTION_HTTP_URL`;
the fetcher already respects robots.txt and rate limits) or a file on a mounted volume
(`INGESTION_FILE_PATH`). Heroku's filesystem doesn't persist, so it needs the URL route. Then set `DEMO_DATA=false`.
